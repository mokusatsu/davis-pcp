# 組込みサンプルを使った継続的な問題発見・修正計画

作成日: 2026-10-05 / 検証開始版: `1c4cc88f53d3e264b275d5b3d88b36f7af787c3a`

## 目的と合格の意味

12種類の実データについて、データの意味を保ったまま読み込み、分析、選択、保存、出力まで進められるかを調べる。見つかった問題は「再現 → 修正前に失敗するテスト → 修正 → 独立レビュー → 回帰 → 実画面の再確認」の順で直す。

画面を開けたことは、その分析が正しいことを意味しない。結果は「合格」「不合格」「仕様どおりの非対応」「未実施」「環境などによる保留」に分ける。数値、操作、保存内容、ダウンロードされた実ファイルは別々に判定する。

対象は既存の組込みサンプルと現在の実装。元データの無断加工、新しいアップロード、未検証の尺度得点の追加は行わない。EDSSのCFA用標本を読み込めても、実装にない確認的因子分析を実施済みとは扱わない。ATOPPは原31項目のまま使い、確定21項目尺度として採点しない。

## 優先順位

1. **最優先: 誤った数値・行・保存内容**。欠損コードの集計混入、重みの取り違え、MAの分母、別データの古い結果、選択行のずれ、保存や出力の欠落を調べる
2. **高優先: 実行できない主要経路**。正しい入力での例外、結果に到達できない操作、切替後の破綻、再開できない保存を調べる
3. **中優先: 誤解を招く表示・不正な入力の受入れ**。尺度・単位・有効行数・不適用理由、コードブック、ラベルとエクスポートの一致を調べる
4. **補助: 表示・性能・長時間利用**。図の拡大、ツールチップ、ブラシ、反復実行、不要な再計算、資源の解放を調べる

## サンプル × 機能の検証範囲

記号: **実** = 有効な入力で実行・値または内容を照合、**境** = 欠損・除外・不適切な入力などの境界も検証、**門** = 不適用の説明や拒否を確認、**―** = この標本ではその機能の検証根拠にしない。これは計画表であり、合格表ではない。

## 第1段階: 入力と数値の土台

- 12標本のハッシュ、行列数、IDの一意性、文字列ID、型、ラベル、尺度、カテゴリ順、欠損コード、MA定義、重み設定、ライセンスを読み取る
- 素朴な数式/NumPy/SciPy/scikit-learnで別実装の期待値を作り、件数・欠損数・平均・分散・度数・相関・重み合計・有効標本数を照合する。同じアプリ関数同士の一致だけで正しさを判定しない
- 生の値とコードブック適用後の値を区別する。真の0、コード欠損、空欄、全欠損、定数列、不十分な有効行を検証する
- Censusでは重み付き/非加重を区別し、非対応の推測統計に通常の検定値が紛れ込まないか確認する
- MAではTokyoとStack Overflowで異なる全ゼロ規約、回答者分母、欠損、選択率と回答数を確認する
- Siechniceでは回答者×課題のまとまり、一組一選択、オプトアウトの構造欠損、属性符号化と反復単位を確認する

## 第2段階: 分析と操作

- PCA/SparsePCA: Iris/Wineの標準化・寄与・復元、実サンプルの得点と直接相関、反復可能性、欠損除外、計算上限、重み非対応の門を確認する
- 因子分析: Türkiye/EDSSを主対象に相関行列、抽出・回転、因子数、非収束/不正行列の説明を確認する。符号や回転不定性を許容した比較にする
- 回帰/分類/クラスタ: Iris/Wineを基本に、適切なカテゴリ目的変数と連続変数を明示し、予測・所属・行IDの対応と決定的seedを確認する
- アンケート: 横浜/掛川のLikert比較、クロス集計、KDA→PRA、欠損方式、Censusの重み、Tokyo/Stack OverflowのMAを深く確認する
- GUI代表ケース: Irisで選択の集合演算・全ビュー伝播・Focus/Delete/Undo/Reset、Wineで分析結果と拡大表示、掛川で欠損とTour、Censusで重みの門、Stack OverflowでMA、Siechniceでコンジョイントを操作する
- 共通図仕様R1～R10を変更箇所と代表図で実ポインタ確認する。クリック、矩形、ホバー、強調、L1/L2、拡大、戻る、連打、キャンセルを区別して記録する
- 31ページの入口と入力適合性を棚卸しし、未選択や不適合列があるときの門を確認する。入口検査を全分析の合格に数えない

## 第3段階: 終了までの作業経路

- データAで分析 → Focus/選択 → データBへ切替 → Aへ戻る。古い結果や行数、列、コードブックがBに残らないことを確認する
- Save/Save As/開き直す/ページ再読込を検証する。共通対象の保存と個別分析結果の保存は仕様上の範囲を分ける
- ローカルAPIの競合token、失敗時の再試行、世代不一致、連続切替で現在の作業が破壊されないことを確認する
- CSV/JSON/コードブック/サンプルZIP/保存分析結果を検証する。行ID、列順、日本語、欠損、数値精度、ライセンスを実内容で照合する
- GUIのダウンロードは実ファイルを読めた場合のみ完了とする。ボタン成功しか見えていない場合はその事実を記録し、実ファイルは未検証とする
- 静的PyodideとネイティブPythonを別環境として比較する。静的版の非対応機能を無理に成功扱いしない

## 修正サイクルと終了条件

1. 新規問題ごとに重大度、最小再現、現在版、期待/実際、証拠、関連セルを記録する
2. 修正前に失敗する回帰テストを追加して原因を限定する。既存変更とデータの意味を保つ最小修正にする
3. 別担当のレビュー後、関連テスト、フロントエンド/バックエンド全体、型、ライセンス、必要なビルド、ネイティブ/WASM、公開版の変更経路を順番に確認する
4. 同じ原因が及ぶ別サンプルと逆順・連続操作を再検査し、計画の未実施セルへ戻る
5. 計画の適用範囲に証拠が揃い、重大な未解決問題がないか、利用者の判断/権限/外部環境が必要な具体的保留だけになった時点で区切る。単に一周しただけで終了しない

公開前に結果と差分を確認する。既存の作業ブランチ以外の公開やmainへのマージはこの計画に含めない。重いビルド・全体テスト・WASM分析を同時に走らせず、ブラウザ資源不足による見かけの故障を避ける。
